# 外部 Harness 统筹

本技能只讲**判断与秩序**：工具的参数与返回值以工具描述和调用结果为准。

## 0. 先认清三件事的归属

| 归属 | 谁提供 | 你该记住的 |
|---|---|---|
| `harness_*` 工具族（12 个） | `@dsh-external/dsh-harness-pilot`（宿主组合挂载） | 派发/跟踪外部 harness 的**唯一**模型面入口 |
| 账号型 LLM 路由 `harness-workbuddy-cn` / `-intl` / `harness-qoder-cn` / `-intl` | `@dsh-external/dsh-model-connect`（宿主组合挂载） | 「点某个桌面登录态账号里的模型」走这里，不经它的 CLI |
| 本地 DSH 子代理 / 工作流 | 宿主 `subagents` 注册表 + 本 preset 的 delegation 行 | `subagent` / `subagent_fork` / `workflow` 是**本地**通道，与外部 harness 是两条路 |

两侧插件各由宿主组合挂载一次。若工具不在目录里，**如实报告缺哪个**，不要假装调用过、也不要自己去 profile 里补挂。

## 1. 选通道：先问三个问题

1. **要等多久？** 分钟级 → 同步；可能几分钟以上 → 后台任务。
2. **中途要不要交互？** 要（多轮追问、看屏幕、点按钮）→ 交互会话；不要 → 一次性派发。
3. **要不要点名模型或账号？** 要 → 只有声明了 `agentOptions` 的目标支持；不支持的会**显式拒绝**，不要靠 `extra_args` 硬塞。

| 通道 | 何时用 | 你拿到什么 | 主要代价 |
|---|---|---|---|
| `harness_dispatch` | 短任务，只要回复文本 | 回复文本 + `[model-ref]` 形式与是否核对过清单 | 同步阻塞；没有 runId 生命周期 |
| `harness_task_start` | 长任务，先拿 id 再继续干别的 | `task_id`，完成后回执唤醒本会话 | 回执可能投递失败/不确定，必须回读 |
| `harness_agent` | 要**子代理生命周期**（runId、stopReason、部分输出、ledger） | runId；`harness_task_status/list` 记 `kind=subagent` | 需要已注册的 provider；不支持 reasoning effort / max tokens |
| `harness_open` + `harness_send` | GUI-only harness、页面内操作、需要人机同屏 | 会话 id + 屏幕文本 | 慢、易受窗口状态影响；模型常只能在它自己的界面选 |
| `subagent` / `subagent_fork` | 只需要 DSH 自己的子代理，不涉及外部产品 | 常规子代理结果 | 不是外部 harness；别把两者混着数 |

补充判据：
- 只要有一丝「这可能跑很久」，就用 `harness_task_start`；`harness_dispatch` 的超时是硬截止，超时后**不会**继续在后台替你跑。
- 同一批互不依赖的派发要**并行起**：一次消息里发多个 `harness_task_start`，不要串行等。

## 2. 侦察（每次派发前的最小动作）

- `harness_list` → 目标名、transport、support 行（acp/headless/window 各支持什么）、命令是否存在。
- `harness_models` → 该目标当前能点名的模型清单。**模型引用只从这份清单里挑**。
- 需要「现在到底通不通」再加 `probe=true`（它会真的碰窗口/端口，有代价）。

目标表随 profile 配置变、模型清单随登录态与额度变——不要凭记忆写目标名或模型名。

## 3. 写自包含任务书（派发质量 90% 在这里）

外部 harness **看不到本会话**，也没有你的工作区记忆。任务书至少包含：

1. **目标**：一句话说清做完的标准（可验证的那种）。
2. **工作目录**：绝对路径；不确定就显式传 `cwd`。
3. **背景**：它需要知道的事实、已经排除的方案。
4. **约束**：能改哪些文件、不许动什么、要不要跑测试。
5. **交付形态**：改代码 / 写报告 / 给 diff / 给命令输出——说清楚你要回读什么。
6. **验收**：怎么算通过（命令、期望输出、检查项）。

反面例子：「帮我修一下这个 bug」。正面例子：「在 `D:\X` 里修 `a.ts` 第 42 行的空指针；只改该文件；`pnpm test a` 必须全绿；把 `git diff` 原文贴回」。

并行派发时每个执行者只拥有互不重叠的文件范围：同一文件不要交给两个 harness 同时改；重叠了就串行，或先让一个只读评审。

## 4. 模型与账号：怎么写引用

- **能点名的模型**：从 `harness_models` 的可选清单里取。纯 id（`Qwen3.8-Max`）与 `<provider>/<model>` 两种写法等价；写错会**先校验、后拒绝**——被拒绝时不会建任务（后台任务连账本记录都不留）。
- **`harness_agent` 的边界**：`model` 作为 per-child `agentOptions` 落到 CLI 命令行；reasoning effort / max tokens 在这条路上**不支持**，传了会被显式拒绝。- **账号**：`accountId` 只在真存在的档案上点名；不存在/已删除 → 显式拒绝，**没有回退**。后台任务那条路：显式 `accountId` > 该目标所属 harness 的池默认账号；不属于本目标的池默认账号会被**忽略并写明原因**。工具输出里账号 id 始终脱敏，把脱敏形式写进结论。
- **GUI-only 目标**：模型常常只能在它自己的界面里选。这时最多报「请求 X，实际未回报」，**不要**报「已切到 X 模型」。

## 5. 失败面：看到这些词时的正确反应

| 你看到 | 含义 | 该做什么 |
|---|---|---|
| `requested` vs `actual` 不一致 | 请求的身份与 harness 自报的身份不同 | 如实报告两者，别只报 requested |
| 字段 `not reported` | harness 没报这一项 | 说「未报告」，**不是**「一致」 |
| `status=stalled` | run 超过预期没动静 | 当作可能挂死：查一次，再决定打断还是换通道 |
| 回执投递 **失败**（明确拒绝） | 结果已落盘，不会唤醒本会话 | 用 `harness_task_status` 读，**不要等唤醒**、不要重放任务 |
| 回执状态 **不确定** | 进程在投递途中结束 | 既不当已送达也不重放；以落盘 `result_path` 为准 |
| `✗ 模型引用被拒绝` | 引用形态或清单核对没过 | 回 `harness_models` 拿清单，改引用；**不要**原样重试 |
| 「账号被拒绝」 | 档案不存在/已删/与本目标不匹配 | 换正确档案或去掉 `accountId`；不要猜 |
| 传输不可用 / probe no | 该 transport 现在走不通 | 换 transport 或换目标；把「为什么不通」写进结论 |

诊断顺序固定：**先读回执与状态 → 再看实际身份 → 再判断产物 → 最后才下结论**。

## 6. 核验：回执不是结论

外部 harness 说「完成」只是一条**证词**。判为完成之前，至少做一件本地取证：

- 文件类：本机读文件 / `git diff` / `git status`，看改动**真的**在。
- 命令类：本机重跑关键命令（测试、构建、lint），看输出。
- 报告/数据类：抽查两三个关键事实（版本号、路径、数字、条数）在本机对得上。

核验不通过时：先补一条**更具体**的任务书重派（带上失败证据），再考虑换目标或换模型，最后才是自己做。不要把「核验失败」静默降级成「大致完成」。

## 7. 交付与汇报模板

一次统筹收尾至少要写清四件事（缺哪条就说缺哪条）：

1. **做了什么**：每个 run 的目标 → 通道 → 实际模型/账号（脱敏）→ 状态。
2. **证据**：本机核验读到的东西（路径、命令、diff 摘要、测试结果）。
3. **没做 / 没验**：被拒绝的派发、被跳过的步骤、读不到的身份。
4. **下一步**：需要用户决定的选项，或建议的后续派发。

读不到、未测量、未回报时，结论里就写读不到 / 未测量 / 未回报——这三样都比一个编出来的「成功」有价值。
